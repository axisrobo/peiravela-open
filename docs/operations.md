# PEIRAVELA-open Operations Manual

Operational runbook for the Apache-2.0 SDK/UI tier of PEIRAVELA. This
repository publishes everything a consumer needs to drive, embed, or
independently verify a PEIRAVELA deployment without depending on the AGPL core:
generated TypeScript and JavaScript clients, the OpenAPI contract and format
schemas, the Studio console, examples, the independent evidence verifier, and
prebuilt AGPL-3.0 core binaries.

This document records raw procedures and configuration facts. It does not
assert service levels or release gates.

## Prerequisites

- **A running PEIRAVELA core** — the SDK, Studio, and examples talk to the
  control-plane `api-server`. Build and run it from the `peiravela` repository
  (see its quickstart). No container or Cloud VM is required.
- **Node.js ≥ 18** — for the generated TypeScript/JavaScript clients and the
  `tsc` typecheck examples (Node 22 is used in CI).
- **PowerShell (pwsh)** — for the independent evidence verifier script
  (`scripts/verify-package-independent.ps1`).

## Using the generated SDK

The generated clients are committed here; they are regenerated by the core
repository (`backend/cmd/gen-client`) and mirrored, so treat them as generated
output, not hand-edited code.

### TypeScript

```ts
import { PeiravelaClient } from "./sdk/ts/peiravela";

const api = new PeiravelaClient("http://127.0.0.1:8080", {});
const health = await api.health();           // store backend + tenant facts
const worlds = await api.listWorlds();       // persisted world records
const runs = await api.listRuns();           // persisted runs with attempts
```

### JavaScript (ES module)

```js
import PeiravelaClient from "./sdk/js/peiravela.js";
```

Both clients use the global `fetch` (Node 18+ and browsers) and throw an
`Error` carrying the server error message on a non-OK response. Set the API
credential by passing headers to the constructor — `Authorization: Bearer <key>`
when it starts with `Bearer `, otherwise `X-PEIRAVELA-API-Key` — mirroring the
core Studio access-control behavior.

### Client surface

The `PeiravelaClient` covers the full control-plane API (31 routes):

- **Discovery**: `health`, `providerSandboxes`, `sutAdapters`
- **Compile/plan**: `compileScenario`, `expandCatalog`
- **Run execution**: `suiteRun`, `matrixRun`, `retainedMatrixRun`, `benchRun`
- **Resources**: worlds, experiments, runs, attempts, branches, source bindings
  (create/list/get, state transitions, lease, destroy, delete)
- **Evidence**: `listEvidence`, `getEvidence`, `exportEvidence`,
  `verifyEvidence`
- **Comparison/audit**: `aggregateControls`, `listAuditEvents`

A compilable example is in `examples/ts-client/`; a JavaScript example is in
`examples/js-client/demo.mjs`.

## Studio

The Studio is the web UI served by the core `api-server` at `/`. The frontend
sources in `studio/` are published here (Apache-2.0) so consumers can theme,
embed, or inspect them. Start the core `api-server`, then open
<http://127.0.0.1:8080/>.

The Studio entry point (`GET /` and `GET /peiravela.js`) is served without
credentials so the sign-in surface can load; when the core has access control
configured, every API route requires it and the Studio shows an
"Authentication required" card on `401`, persisting the entered credential
per-browser.

## Independent evidence verification

Exported evidence packages can be consumed without any PEIRAVELA tooling. The
verifier uses only standard OS tooling (tar + SHA-256) and reads the
self-describing `manifest.json`:

```powershell
pwsh scripts/verify-package-independent.ps1 -Package evidence-package.tar -OutDir ./consume
```

It exits 0 when every artifact digest declared in the manifest recomputes from
the archive bytes; otherwise 1, listing the mismatches. This mirrors what an
external evaluator does — no pass/fail or evaluator judgments are imported.

## Prebuilt binaries

`bin/` holds prebuilt AGPL-3.0 core binaries (`peiravela-api-server`,
`peiravela-control-plane`, Linux amd64 static + Windows amd64 `.exe`), built
from the `peiravela` core with the release version injected via `-ldflags` and
mirrored by `scripts/mirror-binaries.ps1` in the core repository. `bin/` is
gitignored here and committed with `git add -f` at release time, so:

- Verify the embedded version: `bin/peiravela-api-server --version`.
- Release assets are attached to the tags on this repository's Releases page.

These binaries are distributed under AGPL-3.0 terms (see the `peiravela`
repository).

## Release procedure

A release of this tier is driven from the core repository, then mirrored here:

1. The core cuts a tag (`vX.Y.Z`). Core CI builds and vets the full test
   surface and produces versioned AGPL binaries.
2. `scripts/mirror-binaries.ps1` (in the core repo) builds/mirrors the binaries
   into `bin/`, and with `-Upload` creates/updates the GitHub Release on this
   repository with the binaries as assets.
3. The SDK/contracts/Studio surfaces are synced from the core (generated
   clients via `backend/cmd/gen-client`, Studio frontend, contract schemas and
   fixtures), committed here under `sdk/`, `contracts/`, `studio/`, and the
   matching tag is applied.
4. This repository's `release.yml` triggers on any `v*` tag, verifies the
   committed binaries are present and carry the tag version, and uploads them
   to the GitHub Release.

Version numbers here mirror the core tags (e.g. `v0.7.0`). The changelog for a
version records the surface shipped in that tag only; work merged after a tag
goes under `[Unreleased]` and is folded into the next version at tagging time.
Never attribute unreleased surface to an already-shipped tag.

## CI

- **`sdk.yml`** — validates on changes to `sdk/`, `contracts/`, `examples/`,
  `studio/`, and the workflow itself: OpenAPI + schemas parse as JSON, the JS
  client and examples parse with `node --check`, and the TypeScript client
  typechecks (`npm run typecheck`).
- **`release.yml`** — on any `v*` tag, verifies all four binaries exist and
  embed the tag version, then uploads them to the GitHub Release.
